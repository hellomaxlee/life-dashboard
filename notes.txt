# life-dashboard — Project Notes

## Intake (2026-09-26)
Ambition: a single-user life dashboard covering training, sleep, and reading, made visible on a piece of hardware (64x64 pixel matrix). Software and backend first, hardware second.
**Device (2026-09-26): Divoom Pixoo-64 II assumed for all design work; not yet purchased, purchase is Max's call. Reaffirmed 2026-09-27 after weighing e-ink: e-ink fit the twice-daily cadence and the text summary, but Max wants colour and celebration; the full summary lives on the web page to compensate.**
Sources: Apple Health via Health Auto Export REST push (chosen over manual XML and Shortcuts); Goodreads public `read` shelf RSS (API is dead since 2020).
**Strava dropped (2026-09-27):** its API requires a paid Strava subscription. Apple Health already holds every workout the goal model needs (duration, avg HR, HR samples, distance). If Max records in the Strava phone app, the app's Health integration writes the workout to HealthKit and it arrives through the same push.
Hosting: always-on home box on the LAN. **Decision 2026-09-26: run on Max's Mac first (launchd); Max has no Pi experience. Revised 2026-09-27: the Mac is plugged in most of the time and a missed push is acceptable, so the Mac is the home box for the foreseeable future. The Pi is a learning project, not a dependency; the guide lives at `additional/raspberry-pi-guide.tex` and Phase 5 hardware work does not wait on it.** SQLite backups make any move a file copy.
Habits: derived from the data, not manual check-offs.
Progress means (revised 2026-09-26, see § Goal model): 3 quality workouts per week, any sport; a streak of weeks that hit 3; daily small wins (sleep, a quality workout, a finished book); 12 books a year. No event on the calendar. Training load is computed and shown on the web page, not judged on the device.
Phase-1 view: LAN web page previewing the same frames the device will show.
Audience: personal only, single user. No EP role.
Stack: Python, FastAPI, SQLite (Max's choice).
Spend: a small LLM budget for daily summaries. The summary must synthesize the numbers with philosophy and wisdom, balanced, leaning toward sustainable habits and the value of pursuing the goals.
Constraints (derived, not stated): health data stays on the LAN; no device purchase without Max.

## Goal model
v2, answered by Max on 2026-09-26 and 2026-09-27. Every metric cites this section.

| Term | Definition | Config key |
|---|---|---|
| Home timezone | `America/New_York`. Days and weeks are local; a week is Monday 00:00 to Sunday 23:59. | `home_tz` |
| Quality workout | Any type (run, lift, ride, row, swim, HIIT, sport, hike). One rule for all: **effort load ≥ the bar**. Effort load = Edwards TRIMP = minutes in Z1 ×1 + Z2 ×2 + Z3 ×3 + Z4 ×4 + Z5 ×5, computed from the workout's HR samples. No duration floor and no average-HR test; the load carries both. A workout with **no HR samples does not count** (Max, 2026-09-27) and is drawn as a hollow dot on the web page only. Rationale: average HR punishes lifting (rest between sets); time-in-zone lets a hard lift and a 4-mile run earn the same dot. | `workout.load_bar` (placeholder 100 until calibrated) |
| HR zones | Percent of max HR 189 (212 − 23). Z1 95–112, Z2 113–131, Z3 132–150, Z4 151–169, Z5 170+. Below 95 scores 0. | `hr_max = 189`, `zones.pct = [0.50, 0.60, 0.70, 0.80, 0.90]` |
| Load bar calibration | **Revised 2026-10-05 (Max: "turn it down to 30 min"):** the bar is what 30 minutes mostly in zone 2 costs, 30 min x weight 2 = 60, set as `load_bar = 60` with `calibrate = false`, so the run-based calibration below never moves it. Previous rule, kept for the record: the bar is what a 4-mile run costs; placeholder 100; **Automatic, no action from Max (2026-09-27).** First calibration: as soon as three runs of ≥ 4 miles with HR samples exist, the bar becomes the median of their loads, rounded to 5. Re-calibration: every 3 months, from the median of ≥ 4-mile runs in the trailing 3 months, if there are at least three; otherwise the bar is kept. Every change is written to the db with the source workout ids and the date, shown on the web page, and mentioned once by the summary. A bar change applies from the next week forward; past weeks and the streak are never re-scored. | `workout.load_bar`, `workout.recalibrate_months = 3`, `workout.calibration_min_runs = 3` |
| Weekly target | 3 quality workouts per week. Shown as three dots. | `week.target = 3` |
| Rest day | Any day with no quality workout. Rest is never penalized and never breaks anything; Max's work schedule is volatile, so there are no fixed rest days. | — |
| Weeks-hit streak | Consecutive completed weeks with ≥ 3 quality workouts. The current week is in progress and neither extends nor breaks it until Sunday ends. | — |
| Daily small wins | (a) slept ≥ 7.0 h last night; (b) a quality workout today; (c) finished a book today (Goodreads `read` shelf gained an entry). Each win gets a small on-device reinforcement. Steps are **not** a target (Max, 2026-09-26: the quality workout is what matters); they are shown as a plain number and feed nothing. | `sleep.target_hours = 7.0` |
| Week complete | Third dot filled → a party animation plays on the device. Once per week, at the moment the third workout lands. | — |
| Reading | Books on the Goodreads `read` shelf with a read-at date in the current calendar year, target 12. **Feed checked 2026-09-27:** 75 items, only 19 carry `user_read_at`, 1 in 2026; `user_date_added` is always present (1 in 2026). Rule: use `user_read_at`; when it is empty, fall back to `user_date_added` and mark the book as date-inferred on the web page. Max can fix dates on Goodreads any time and the next poll picks them up. | `books.target_per_year = 12`, `books.fallback_to_date_added = true` |
| Sleep | A session belongs to the day you wake. Shown against 7 h; a metric and a daily win, not a streak. | — |
| Wellness signals | Stored daily, never a target or a win (Max, 2026-09-27): **HRV** (overnight SDNN), **resting heart rate**, **VO2 max** estimate, **time in daylight**. Each gets a 28-day rolling baseline; a deviation beyond a configured band (HRV −20 %, resting HR +5 bpm, daylight < 20 min) is a fact the summary may state, never a verdict. **At most one wellness fact per summary, and only on a band crossing; on ordinary days the summary ignores them entirely** (Max, 2026-09-27: keep summaries light). Shown as trends on the web page; VO2 max monthly. Not on any device panel. Logged-only metrics (mood, mindful minutes, weight, intake) are excluded. | `wellness.baseline_days = 28`, `wellness.bands = {hrv_pct: -20, rhr_bpm: 5, daylight_min: 20}` |
| Claude usage meter | Thin bar under the Week panel's dots showing the seven-day Claude subscription window from Claude Code's status-line feed (`rate_limits.seven_day.used_percentage`, `resets_at`). A status-line hook writes the JSON to `data/claude_usage.json`; ingest archives it raw and stores `claude_week_used_pct` and `claude_week_resets_at` in `daily_metrics`. Label reads "resets in N d", never "this week", because the window is rolling. Refreshes only while a Claude Code session is open; the bar shows its age past 24 h and never blanks. Not a target, not a win, not in the summary. Design and acceptance: issue #2. | `claude_usage.path`, `claude_usage.stale_hours = 24` |
| Pull schedule | Health Auto Export pushes **every 6 hours** (Max, 2026-09-29; supersedes 06:30/22:00), two automations (Workouts, Health Metrics), each carrying the previous 7 days so a missed push is refilled by the next. Goodreads polled at 06:30. Claude usage file read whenever it changes. The Today panel shows last night's sleep and today's dot as of the last push with an "as of HH:MM" mark. A week closes after the first push following Monday 00:00 local, so a Sunday-night workout still counts for its week. The party for a third dot plays at whichever push brings it. | `pull.health_interval_hours = 6`, `pull.goodreads = "06:30"` |
| Training load | HR-based TRIMP, 7-day acute and 42-day chronic EWMA, balance = acute/chronic. Computed for every day, displayed on the web page and in the summary; not a device screen in v1. | — |
| Dedupe | Copies of one workout from several HealthKit source apps are one activity (issue #4, rulings 2026-10-02). Different apps: start within 5 min and duration within 10 %. Same app (a phone app re-issuing a workout under a new id): only when the two time intervals overlap; back-to-back workouts from one device never merge. Chains join (A~B and B~C make one activity). The copy with the most HR samples names and describes the activity, the longest distance wins, every provenance is kept. A workout deleted in Health is withdrawn, not deleted, and counts for nothing. Detail: § Architecture assumptions, Dedupe rows | `ingest.dedupe.start_window_min = 5`, `ingest.dedupe.duration_tolerance_pct = 10` |

Rotation on the Pixoo, in order: **Week** (three dots + weeks-hit streak) → **Today** (last night's sleep vs 7 h, today's dot as of the last push with an "as of HH:MM" mark, steps as a plain number) → **Books + summary line** (books this year vs 12, one-line daily summary scrolling). Load screen dropped from the device rotation at Max's request; it lives on the web page.

Design brief from Max: "Be clever and creative and colorful." Wins are celebrated; misses are shown plainly, never nagged.

## Voice brief
Answered by Max on 2026-09-27 and accepted the same day without edits; his one-line bar for every summary is **wise and thoughtful**. Theodora drafts from this; Ingrid ratifies. Every summary is judged against it.

**Sources it may draw on.** Stoic practice (what is in my control, the obstacle as material, the evening review); Aristotle on habit (we are what we repeatedly do, virtue as a mean, practical wisdom); Buddhist non-attachment (the effort is yours, the result is not; begin again without drama). Qualities Max admires and the voice may embody without naming anyone: steady leadership of oneself, resilience under discomfort, honest self-awareness about one's own biases.

**Rule on names and voices (revised 2026-10-04 at Max's request: direct quotes welcome).** No impersonation: never speak as a person or in a pastiche of anyone's style, and nothing attributed to or styled after a living person. A direct quotation is welcome, with its author named, only when it is an entry in the quote bank (`app/summary/quotes.py`: 81 entries, deceased authors, each with work and location), copied whole and unchanged; the bank exists because a model asked for "a quote" will sometimes invent one. A person is named only as the author of the bank quote in that line; no "as X said" or "X would say" with other words. A tradition may be named in paraphrase ("the Stoics", "an old Buddhist idea"). The same quote or author does not return within 14 lines. The gate enforces all of it.

**Register (revised 2026-10-04).** A quiet friend who noticed. Mindful, practical philosophy first: the thought leads and the day's data is context, touched roughly one day in three or when a number truly illustrates the thought; never a recap of the stats, and a line with no number is welcome. Calm, occasionally wry, never a coach, never a preacher. Second person, present tense. **Never say or imply he rested or did not train** (Max, 2026-10-04: "never assume weekends are rest days"): no workout on record is absence of a record, not evidence of rest, on weekends as on any day; say "no workout on record" if it must be named, and write about rest only as an idea.

**Shape (revised 2026-10-04).** One line for the device, at most 220 characters including any quote and attribution (the panel pages it, about half a minute at full length; shorter is welcome). Either an original reflection or `"quote" - Author` with an optional short connecting clause. An optional second sentence on the web page only. Health data missing, a workout without heart rate, and a workout under the bar are named plainly beside the thought; a finished book is named. Every number outside a bank quote is a lookup from the metrics payload.

**Minimize repetition (Max's explicit ask).** Three mechanisms, all enforced in code, not by hope:
1. *Lens rotation.* Each day is assigned a lens from a seven-day cycle: control / habit / non-attachment / self-awareness / resilience / rest-as-work / plain gratitude. The prompt receives only that day's lens.
2. *Recent-lines memory.* The prompt receives the last 14 device lines and must not reuse their opening three words, their central image, or their named source.
3. *Similarity gate.* A new line whose trigram similarity to any of the last 30 exceeds a threshold (start at 0.5, tune on real output) is rejected and regenerated once, then falls back to rule-based copy.

**Ban list, seed.** Grows from real rejections. Rejected on match, case-insensitive:
"don't break the chain", "no excuses", "crush", "grind", "beast", "lazy", "should have", "you failed", "only N left", "disappoint", "stay hard", "no days off", "hustle", "guilt", "shame", "you need to", "you must", "just do it", any exclamation mark, any emoji, any second exclamatory clause.

**Hard days.** A week that ends at one dot gets a true sentence, not a consolation. The line names what happened, then places it. It never asks for more next week and never mentions the streak that ended.

**Ten hand-written lines across the fixture cells** (day type × completeness × streak × season). These are the contrastive examples for the prompt and the first golden cases for the gate.

| Cell | Line |
|---|---|
| train / all sources / alive / base | "Every habit and faculty is maintained and increased by the corresponding actions: the habit of walking by walking, the habit of running by running." - Epictetus |

**Lines Max would hate (the negative examples).** "Rest day Saturday, 12547 steps." · any quote from memory rather than the bank · a stats recap · "Don't let the streak die!" · "Only one more and you're done!" · "You slacked off yesterday." · "As Marcus Aurelius said, ..." (twice in a week) · "Be a beast." · Any line with a number that is not in the payload.

**Fallback copy.** Rule-based, from templates keyed by the same fixture cells, using the same lens rotation, so the device never blanks and the fallback is not visibly worse for a day.

## Architecture assumptions
| Area | Decision | Rationale |
|------|----------|-----------|
| Storage | SQLite, one file, hand-written migrations | one user, one box; backup is a file copy |
| Raw archive | every inbound payload written verbatim to `data/raw/<source>/<utc-ts>_<sha8>.json` (`.xml` for goodreads) before parsing | recompute any metric from scratch; replay is the idempotency proof |
| Health export | Health Auto Export app posting JSON to `POST /ingest/health` | HealthKit has no server API; the app is the least-manual path |
| Strava | Not a source, not an import. Removed entirely | the API needs a paid subscription; Health has the same workouts |
| Reading | Goodreads shelf RSS polled daily | the only supported channel left; CSV export as a manual backfill |
| Goodreads poller | `app/ingest/goodreads.py` (2026-10-02). The one outbound call is a GET of `GOODREADS_RSS_URL`; the host must be `www.goodreads.com`/`goodreads.com` over https and every redirect is refused, so no other host can be reached even if the secret changes. Raw first: the exact bytes land in `data/raw/goodreads/<stamp>_<sha8>.xml` (the archive's first non-JSON source; `health.raw_suffix` maps source → extension). An unchanged shelf serves byte-identical feeds (`lastBuildDate` is the last shelf change, not the fetch; two live fetches 2 s apart shared one sha256), so a repeat poll is a sha duplicate and no canonicalisation is needed; a byte-different feed of the same shelf changes no data table (pinned by test). Parsing is stdlib `xml.etree`; items are keyed by `book_id` (falling back to `<book id>`), an item with no id or no title is skipped and logged. Dates: `user_read_at` is a calendar date (Goodreads emits `00:00:00 +0000`), stored as that day's midnight America/New_York in UTC so `local_day()` returns the chosen day; `user_date_added` is an instant (Pacific offset) converted to UTC. Accepted formats: RFC 822 as Goodreads writes it (day padded or not, weekday and seconds optional, numeric offset, GMT/UTC or a US zone name) and ISO 8601; anything else is null and logged, never guessed. Fallback rule per § Goal model: empty or unreadable read-at + `books.fallback_to_date_added` → `read_at = date_added`, `date_inferred = 1`; rule off → null. Upsert: the feed is authoritative for what it carries (a fixed date replaces the old one); a book removed from the shelf is **not** deleted. Scheduler: cron at `pull.goodreads` local time, misfire grace 18 h, guarded, fresh connection per run; on start, if no parsed feed arrived in 24 h (first boot, long sleep, or simply no shelf change in a day, since duplicates add no row) one poll runs 3 min after start. No `GOODREADS_RSS_URL` → job not registered, `tools.sync --source goodreads` exits 2 with a message. Phase 2 derives books YTD and the finished-a-book win from `books`; the poller computes nothing | the feed is the only Goodreads channel; a calendar date stored as a UTC instant must survive `local_day()` or the year boundary moves (a 31 Dec read-at added at 21:30 Pacific is 1 Jan in New York); keeping removed books means a shelf cleanup never erases a year's count |
| Frames | Pillow → 64x64 RGB frames; a *clip* is a list of frames with per-frame durations; adapters transport (Pixoo local HTTP API, file) | keeps the device swap to one adapter; celebrations need animation |
| Summary model | Anthropic SDK; id pinned in config; monthly cap enforced in code | budget is small and must be a hard stop |
| Time | store UTC, compute days in the home timezone | streaks and sleep depend on local day boundaries |
| Day-grouped metrics and sample pushes | Two push shapes, detected per metric (issue #3, 2026-10-02). **Day-summed** rows (every row stamped midnight in its own offset, or a bare date) keep the phone's calendar date; only sleep wake-day and workout times are re-projected UTC→America/New_York. **Samples** (the shape every real push has had: ~100k rows per 7 days, per-second step and daylight slices, one sleep row per stage segment) are reduced in the parser to one value per America/New_York day and the stored source label names the rule: steps and daylight are summed per (day, source label); when the day's labels NEST (one label lists every source the others carry, the minute-grouped shape of 2026-10-07: `Watch\|iPhone` for most minutes, `Watch` alone for the rest, no stamp under two labels) the phone merged the sources per stamp itself and every row is summed under the widest label; when standalone labels sit side by side (`Apple Watch` beside `iPhone`, the per-second shape, both devices seeing the same steps) the day takes the LARGEST source total, never the sum across sources (ratified Ingrid, 2026-10-07, after largest-label stored 12133 for 2026-10-06 against a true 12428; mutant and golden in `tests/ingest/test_samples.py`, fixture `metrics_v2_minutes.json`) → `<source> (summed)`; HRV is the mean of the day's readings across sources → `(daily mean)` (the Watch reads HRV through the day; the overnight subset is not identified, so the stored figure matches the Health app's daily average, not the overnight SDNN the wellness row names); resting HR and VO2 max take the latest reading of the day → `(latest)`; `heart_rate` is pushed although the automation omits it and is ignored without being listed as unknown. Sleep: a row with a night total or night start (`asleep`, `totalSleep`, `inBed`, `sleepStart`, `inBedStart`) is a summary; a row with a stage `value` and start/end is a segment. Per source, segments sorted by start; a gap over `ingest.sleep_gap_min` (60) between one segment's end and the next's start closes the session. `in_bed_s` = span, `asleep_s` = Core + Deep + REM + unspecified Asleep, never Awake or InBed; stage seconds come from the segment's own start/end, not `qty`; a stage with no segment is NULL; wake day = home day of the end; a nap is a session like any other (the view and the engine take the longest `asleep_s` of the wake day). **Window edges:** the push covers the 7 whole phone-local days ending yesterday (seen on every real push: today's steps and last night's sleep are never in it, so the Today screen is a day behind by the app's window, not by ingest). Days inside the window are complete and last received wins. A night that began before the window's first midnight would arrive cut, so a session built for the window's first day never replaces a stored session of the same wake day and source that began before the window and overlaps it (store.replace_sleep); nothing stored yet → the cut session is stored.
